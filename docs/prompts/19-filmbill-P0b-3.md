## Part 4 — number series
Spec from `03-` §4, with decisions added below.
- Model `NumberSeries` (company, `document_type`, name, pattern, `reset` never/yearly, `next_value`, `current_period`, `padding`, active) and an **allocations** table (series, period, value, number, **document_date**, allocated_at, entity reference nullable). One active series per company and document type.
- Tokens: `{YYYY}`, `{YY}`, `{MM}`, `{SEQ}`, literal text. Example `AR-{YYYY}-{SEQ}`, padding 4 → `AR-2026-0001`.
- `allocate_number(db, company_id, document_type, document_date)` returns a small result `{number, warnings}`: `SELECT … FOR UPDATE` on the series row, yearly reset from `document_date`, increments, formats. **No commit of its own**: a rollback of the caller does not consume a number.
- Seed per company at creation **and backfill existing companies in the migration**: `quote`, `order_confirmation`, `delivery_note`, `invoice`, `credit_note`, `self_billing`, `dunning`, `letter` with prefixes AN, AB, LS, AR, KR, GS, MA, BR. User-editable.
- **Validation:** a pattern must contain `{SEQ}`. A series with yearly reset must contain `{YYYY}` or `{YY}`; otherwise the numbers repeat every January and the numbering stops being unique. Refuse with a readable sentence.
- **Continuous numbering is a real option, chosen per series (Mathias's decision).** `reset = never` means the counter never restarts: `AR-0001, AR-0002 …` or, with a year token, `AR-2027-0412` continuing from the previous year. A year token is allowed with `never` (it prints the year, it does not restart the count). Seeded default stays yearly (`AR-{YYYY}-{SEQ}`); the Number series screen offers "Restart every year" / "Continue without restart" as a plain choice with one line of help each, and the live preview shows the next number under the chosen mode.
  **Switching modes:** yearly → continuous keeps the counter exactly where it is (no gap, no repeat). Continuous → yearly takes effect at the next period boundary, not immediately; the screen says so. Both switches are audited (Part 5) with old and new mode, and neither may re-issue an allocated number. Tests: switch mid-year in both directions; year rollover under `never` keeps counting; year rollover under `yearly` restarts at 1.
- **Collisions:** `unique (series_id, number)` on allocations. A pattern change that would re-issue an existing number is a 409 naming the number, never a duplicate.
- **Lowering `next_value`** is refused if it would re-issue an allocated number.
- **Out-of-order dates: allowed with a warning (decided 2026-10-20).** A `document_date` earlier than the latest `document_date` already allocated in the series is **allowed** and returns the warning `document_date_before_latest` (with that latest date and the number it belongs to). It is never an error and never silent.
  - `yearly` series: a date in an earlier period allocates from **that period's own counter** (highest allocated value in that period + 1, or 1 if the period has none), computed under the same row lock on the series. The current period's counter is untouched.
  - `never` series: the number is simply the next one; the warning says it is out of date order.
  - An audit event `number.out_of_order` is written in the caller's transaction when it happens (Part 5).
  - A **preview endpoint** takes an optional date and returns the number that *would* be allocated plus the same warning, without allocating. The Number series screen has a date field next to the live preview that shows it.
  - The finalize screen does not exist until P2. Record in SCOPE §16 (Part 7) that P2's finalize flow must show this warning and require an explicit confirmation. Say in the report that this rule is **not tax-advised** and needs the Steuerberater's confirmation.
  - This is the riskiest rule in the part. Test the old-period counter hardest (see tests and mutations).
- **Padding overflow:** when the value exceeds the padding (10000 with padding 4), the number grows (`AR-2026-10000`); it never truncates or wraps. Test it.
- Timezone: `document_date` is a date. When the caller has only a timestamp, the period is derived in the **company's timezone**. Test 31 Dec 23:30 UTC against a Vienna company.
- Admin UI: Settings → Company → Number series, create/edit, **live preview from an API preview endpoint** (the web app never formats or increments, rule 2). Permission keys: list every new one in the report.
- Cross-company isolation (rule 6): new endpoints join the OpenAPI-derived isolation test automatically; show that they were caught first and then covered.

Tests (real Postgres, declared): **20 threads × 50 allocations on one series → 1000 distinct numbers forming exactly 1..1000, no gaps**; a thread that rolls back leaves no gap; yearly reset on 1 Jan in company timezone; padding overflow; pattern validation cases; downward `next_value` refused; **mixed concurrency: threads allocating into the current period and into an earlier period at the same time → each period's numbers are distinct and gap-free**; back-dated allocation returns the warning and writes the audit event; a back-dated allocation never changes the current period's counter; preview with and without a date allocates nothing.
**Mutations, a real FAIL line each:** remove `FOR UPDATE` (the concurrency test must fail; if it does not fail reliably, raise the contention and say so); remove the `{YYYY}` validation; let `allocate_number` commit; compute the earlier-period counter from `series.next_value` instead of that period's allocations (the mixed-concurrency or duplicate test must fail); drop the warning.
