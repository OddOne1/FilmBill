## Part 0 — Change country (own commit, before any party work)
Today the pack is installed once, when the country is first set; changing the country later installs nothing, and a company that mis-set DE and corrects to AT stays on German codes. Fix it for good.
- **First set** (company has no tax rows): unchanged, seeds as today, no dialog.
- **Any later change** goes through an explicit **plan → confirm** flow. `POST /company/tax/country-change/preview {country}` returns a plan; `POST /company/tax/country-change {country, mode}` applies it in one transaction. `mode` is `apply_pack` (recommended) or `country_only` (changes the country and nothing else). The Company screen's Country field opens a dialog with the preview; no code path changes `address_country` on a company that has tax rows without one of these two modes being chosen.
- `apply_pack` behaviour, **non-destructive**:
  - adds the new pack's codes that do not exist yet (by code string);
  - re-points the shipped classes (`standard`, `reduced`, `reduced_2`, `reduced_3`, `zero`) to the new pack's code for the same key; a shipped class whose key the new pack lacks is **kept as it is** and listed as "no equivalent in the new country";
  - never changes a rate, name, note or active flag the user edited; never touches a user-created rate (`custom_*`) or no-tax case;
  - old-country pack codes: deactivated if nothing references them (use the P1a-2 reference registry), kept active and listed if something does;
  - the old pack's unedited rules are replaced by the new pack's rule set (the same shape across packs; report any difference you find);
  - if the new country's standard class resolves to an inactive code (a country without a pack, or one still at "set your rate"), the preview says so in plain words: "proposals will be blocked until you set your rate".
- The preview lists, in plain words and counts: codes added, classes re-pointed, codes deactivated, codes kept because referenced, things of yours left untouched, and warnings. Applying produces exactly what the preview showed (test this).
- One audit event `company.tax_country_changed` with old country, new country, mode and the counts, in the caller's transaction. Finalized documents are unaffected by design (P3 snapshots); say so on the dialog in one sentence.
Tests (real Postgres): AT → DE → AT round trip leaves the same active shipped codes as fresh seeding; an edited rate survives a switch; a user-created rate and no-tax case survive; a referenced old code stays active (register a referrer in the test); preview equals applied result; `country_only` changes nothing else; first-set path unchanged; FR (no pack) path; another company's data untouched; permission and isolation matrix.

## Part 1 — data model and the pure resolver (migration, rule 9)
All tables carry `company_id` and join the cross-company isolation test.
- `parties`: `id`, `company_id`, `type` (`organisation` | `department` | `person`), `parent_id` (nullable, same company; **organisation has no parent; department's parent is an organisation; person's parent is an organisation, a department, or none**; database check or validated constraint plus service validation; no cycles), `name`, `trading_name`, `legal_form`, `register_number`, `register_court`, `is_customer`, `is_supplier`, `is_partner`, `tags` (array), `party_number` (text, unique per company when set), `language`, `default_currency`, `payment_terms_days` (int, nullable) and `payment_terms_text`, `po_reference`, `notes`, `business_status` (`auto` | `business` | `private`, default `auto`), `tax_country` (ISO-2, nullable), `vat_id` (normalised, nullable), `tax_override` (JSONB in exactly the shape the engine's `party_override` takes, nullable), `einvoice_routing` (JSONB: `peppol_id`, `leitweg_id`, `at_einvoice_id`, all optional), person-only fields (`title`, `position`), `is_active`, timestamps.
- `party_addresses`: party, `kind` (`billing` | `delivery` | `postal`), street lines, zip, city, country (ISO-2), `is_default` per party and kind.
- `party_contact_points`: party, `kind` (`email` | `phone`), `value`, `label`, `purpose` (`general` | `invoice`), `is_primary`.
- `party_bank_accounts`: party, label, IBAN (normalised exactly like the company's: compact, upper case), BIC, bank name, `is_default`; unique `(party_id, iban)`.
- `party_vat_checks`: **append-only** history (UPDATE/DELETE blocked by trigger like `audit_events`): party, `vat_id`, `country`, `status` (`valid` | `invalid` | `unavailable` | `not_applicable`), `response` JSONB, `consultation_ref` nullable, `checked_at`, `checked_by`.
- **Customer/supplier numbers** use the number-series machinery from P0b-3: add document types `customer` and `supplier` (defaults `K-{SEQ}` and `L-{SEQ}`, `reset: never`, padding 4), seeded for new companies and **backfilled for existing ones in the migration**. `party_number` is allocated from the matching series when a party is first flagged customer/supplier and has none; it stays editable (unique per company); allocation happens inside the same transaction as the party write.
- **The resolver** (`apps/api/billing/parties/`, pure Python, same import-boundary test as `billing/tax/`): `resolve_recipient(chain) -> ResolvedRecipient`, where `chain` is the list person → department → organisation as plain value objects. Rule (SCOPE §3): each field is the first non-empty of person → department → organisation; **billing address and VAT ID always from the nearest level that has them; the contact name stays the person's**. Output carries, for every field, its value **and its source level**, so the UI can grey inherited values and name the origin. The result is a plain, detached value object (no ORM objects), so P2 can store it as the document snapshot. Also: `recipient_buyer_type(resolved)` → `business` | `private` with the reason (`explicit`, `organisation`, `person_with_vat_id`, `person`), and `tax_inputs(resolved)` producing exactly the engine inputs from Step 0 item 3 (`buyer_country`, `buyer_type`, `buyer_vat_verified`, `party_override`). **Business rule (decided): `business_status = auto` means business if the party is an organisation or has a VAT ID; a person without one is private; `business` / `private` override the derivation.** Shown on the party with its reason.
- Golden fixtures (S5 and more): contact without address under a department without address → the organisation's address, source `organisation`; contact name stays the person; department's own address wins over the organisation's; VAT ID inherits from the organisation; changing the organisation's address afterwards changes a fresh resolver result but **not** a previously stored value object; a person with no parent resolves from itself; business derivation for each of the four reasons.
- Validation tests: cycle refused; wrong parent type refused (409 with a readable sentence); cross-company parent is 404; depth cannot exceed three levels.
**Mutations, a real FAIL line each:** take the contact name from the organisation; skip the department level; let the billing address fall back to the person's postal address; allow a cross-company parent. Revert.

## Part 2 — VAT ID handling and VIES
- **Normalise**: strip spaces, dots, dashes, upper-case; split into country prefix and number. **Greece is `EL` in VIES but `GR` as ISO country**: map explicitly and test it. The accepted-format table per EU country (and `XI` for Northern Ireland) lives in a data file (`region_packs/vat_formats.yaml`), not in code; a wrong format is a 422 with a readable sentence before any network call. Non-EU countries (CH, GB, US, …) are accepted as free text with status `not_applicable` (VIES does not cover them).
- **VIES client** `services/vies.py`, with an injectable transport. **Read the official VIES REST documentation first and state in your report which endpoint and request shape you used and where you read it**; do not guess. Timeout about 8 s, one retry, no secret in logs. **Tests never call the real service**: a fake transport covers valid, invalid, malformed, member-state-unavailable, timeout, 5xx and rate-limit responses.
- **Mapping rule (important):** any failure to *obtain* an answer is `unavailable`, **never** `invalid`; `invalid` only when VIES positively says the number is not valid.
- `POST /parties/{id}/vat-check` runs the check for the party's current VAT ID, appends a `party_vat_checks` row, and returns it. **`buyer_vat_verified` is true only if the latest check for the party's *current* VAT ID is `valid`**; changing the VAT ID, its country, or the party's organisation parent resets it. Store what VIES returned (name, address as returned, consultation reference if any) and show it next to the party's own name and address with a plain "differs" marker; do not auto-correct anything.
- Offline-friendly: a self-hosted install with no internet gets `unavailable` with a clear message and the party remains usable; no check is ever required to save a party.
- State plainly in the UI and docs what this check is: a VIES lookup of record, **not** the qualified confirmation procedure of a tax authority [Likely: the qualified confirmation is a separate FinanzOnline/BZSt procedure; do not claim this check replaces it, and add it to the Steuerberater question below].
**Mutations, a real FAIL line each:** map a timeout to `invalid`; skip the reset when the VAT ID changes; treat `unavailable` as verified. Revert.
