## Part 1 — model: strips over days (migration)
- New table `project_blocks` ("strips"): `project_id`, `company_id`, `type` (one of `PROJECT_DAY_TYPES`, the strip's main type), `label` (free text, e.g. "Documentary shoot", "BTS"; nullable), `start_date`, `end_date` (`start_date <= end_date`, enforced in the schema), `location` (nullable), `default_call_time`, `default_wrap_time` (nullable), `notes`, `is_active`, timestamps, `position` (lane hint, nullable). Soft removal only, as for days.
- `project_days.block_id` nullable FK to `project_blocks`. **Days stay the single source of truth for counts**: a strip owns one active day row per date in its range, each with its own `type` (the strip's main type, or an override such as `travel` or `off`). Replace the unique index with `(project_id, date, block_id)` where active, so two strips may cover the same date, and one strip never has two rows on one date. Days without a block (older data) remain valid.
- **Counting:** `days:<type>` counts **distinct dates** having an active row of that type, across all strips. Two overlapping shoot strips on 4 March count that date once; a date that is shoot in one strip and travel in another counts once as shoot and once as travel. Record this as **[Guessing], an open decision for Mathias**. Update `count_days_of_type`, the globals' sync and their tests; the stored global values must come out **identical** to before for every existing project.
- **Optional strip filter on globals:** a global's source may name one strip, `days:<type>:<block_id>`, counting that strip's days of that type; the globals panel offers it as a picker "all strips / this strip". A removed strip's global falls back with a visible warning, never silently to zero.
- **Data migration of existing days into strips (state the rule and test it):** walk each project's active days by date; a **run** is consecutive dates (Saturday and Sunday gaps with no row are bridged) in which every day is the run's main type or `travel` or `off`. The main type is the type of the run's first day that is not `travel`/`off`; a day of any other type ends the run. Each run becomes one strip (label null, location and times from the first day that has them) and its days get `block_id`; a run made only of travel/off days becomes a strip of that type. Example from Mathias's real project, which a test must reproduce: prep 30 Nov–2 Dec, shoot 3–4 Dec, travel 12 Jan / shoot 13 Jan / travel 14 Jan, travel 22 Feb / shoot 23–27 Feb / travel 28 Feb, post 1–12 Mar gives five strips (prep, shoot, shoot with a travel day at each end, shoot with a travel day at each end, post) and **per-type day counts identical before and after** (3 prep, 8 shoot, 4 travel, 12 post for that project). Downgrade drops the strips and the column and restores the old index.
- Audit, caller's transaction: `project_block.created|updated|moved|resized|removed`, `project_block.days_set` (one event with counts), no per-day event storms. Permissions: `projects.view` reads (staff included, as today), `projects.edit` writes; no new keys.
Tests (real Postgres): migration up/down with the example above; overlapping strips on one date; the distinct-date counting with the three overlap cases; one row per date per strip; the strip-filtered global; isolation matrix and the staff walk for the new routes; no DELETE route in OpenAPI. **Mutations, a real FAIL line each:** the count adds overlapping same-type days twice; the migration changes a per-type count; a strip accepts two rows for one date. ## Part 2 — API
- `GET /projects/{id}/calendar?from=&to=` returns the strips intersecting the range, each with its days (date, type, location, times, notes, is_override), plus the **per-type counts (distinct dates)** for the whole project; the web never counts.
- `POST /projects/{id}/blocks` (type, label, start, end, location, default times, `weekends: "off" | "same"`: weekend dates inside the strip are created as `off` rows or as the main type), `PATCH /projects/{id}/blocks/{id}` (label, type, location, times, notes), `POST …/blocks/{id}/move` (new start date, days shift by the same offset, overrides and per-day data travel with them), `POST …/blocks/{id}/resize` (new start and/or end: growing adds days of the main type, shrinking soft-removes days outside the range; if any removed day carries notes, times or a location the response **requires** `confirm: true` and lists them), `PUT …/blocks/{id}/days` (a list of `{date, type | null}`: `null` returns the day to the strip's main type; types from `PROJECT_DAY_TYPES`), `POST …/blocks/{id}/duplicate` (to a new start date), `POST …/blocks/{id}/remove` (soft, with a count of days affected).
- Per-day details (location, call, wrap, notes) keep the existing day endpoints. A day with no value of its own shows the strip's default.
- The old `/days` and `/days/range` endpoints keep working (the budget example and any consumer use them); a day created through them has no strip and appears in the calendar as a single-day strip of its own type.
Tests: every route above including the confirm rule on resize, move carries overrides, duplicate, the old endpoints still counted, validation (dates, types, other company's project = 404), generated types regenerated. **Mutation, a real FAIL line:** resize drops days that carry notes without the confirm. Revert.

## Part 3 — the calendar screen (replaces the Days tab's top part and table)
- **Layout:** the full available width, no narrow centred column. A **month grid** (weeks as rows, Monday first, week numbers, weekends shaded, today marked, the project's start and end date marked), with **previous/next month and "today"**, and above it the existing **overview strip of the whole project** as a navigator (click a month to jump). Type colours and legend as today.
- **Strips are drawn as bars across the days they cover**, wrapping across week rows like a multi-day event in a calendar app, labelled with label (or type) and location. **Overlapping strips stack in lanes**; a day cell that has more strips than fit shows "+N" that opens the list for that day. Days inside a strip that are overridden (travel, off, …) are visibly different (own colour or hatching) and travel days show a small plane or "T" mark.
- **Creating:** drag across empty days (or click one day, then shift-click another) opens a small popover: type, label, location, "weekends off" checkbox, Create. An **Add strip** button does the same from keyboard with date fields.
- **Editing:** clicking a strip opens a side panel with label, type, start and end date, location, default call and wrap, notes, and the **days of the strip as a row of day chips**. Clicking a chip selects it (shift-click for a range, ctrl/cmd-click to add); buttons act on the selection: **Mark as travel**, **Mark as off**, **Back to main type**, plus a type selector for any other override; quick buttons **First day = travel** and **Last day = travel**. Expanding a day shows its own location, call, wrap and notes. Buttons to **Duplicate** and **Remove strip**.
- **Direct manipulation:** drag a strip's body to move it, drag its left or right edge to resize it (with the confirm dialog when days with data would be removed). **Every action must also be possible without dragging** (the panel's date fields, the buttons, keyboard), because the tests and some users will not drag. Strips are focusable, Enter opens the panel, Escape closes it.
- The old day table survives only as a **List** toggle (read and edit per-day details, sorted by date), collapsed by default; it must not be the default view any more.
- Without `projects.edit`: nothing editable, buttons absent, a sentence says why (17c); staff see the calendar read-only.
- Behavioural component tests with the real API response shapes, driven by pointer events and keyboard: drag-create, click-create, open the panel, mark a middle day as travel and see the counts change, overlapping strips in lanes with "+N", move and resize through the panel and by dragging, the confirm dialog, read-only mode, the list toggle. **Mutation, a real FAIL line:** the screen computes the day counts in the browser instead of rendering the API's. Revert.
