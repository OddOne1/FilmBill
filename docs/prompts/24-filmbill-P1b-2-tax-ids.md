## Part 1 — tax IDs become their own entity (migration)
Today a party has one `vat_id`. A party needs several typed identifiers.
- New table `party_tax_ids`: `id`, `company_id`, `party_id`, `kind` (`vat` | `uid_ch` | `abn` | `ein` | `tax_number` | `company_register` | `other`), `country` (ISO-2), `value` (normalised per kind), `is_primary`, `is_active` (retire, never delete), `notes`, timestamps. Unique `(party_id, kind, value)`. A party has at most one primary active ID per kind-group `vat-like` (`vat`, `uid_ch`, `abn`) which is the one the resolver uses for the buyer.
- Normalisation rules per kind in data (extend `region_packs/vat_formats.yaml`): EU VAT as in P1b (EL/GR mapping kept); `uid_ch` = `CHE-123.456.789 MWST|TVA|IVA` with the MOD11 check digit validated (read eCH-0097 or the register's own documentation for the algorithm and cite it); `abn` = 11 digits with its published weighting check (cite the source). A wrong format is a 422 with a readable sentence before any network call. `ein`, `tax_number`, `company_register`, `other` are accepted free text, never auto-checked.
- **Migration**: create the table, copy each existing `parties.vat_id` into a primary `vat` row (kind `uid_ch` if the country is CH and the value matches that shape), repoint existing `party_vat_checks` rows to it, then remove `parties.vat_id` from the write path and drop the column in the same migration (one source of truth). No real data exists; do it cleanly. Remove the P1b `POST /parties/{id}/vat-check` route in favour of Part 4's, and update every test and the web (Step 0 item 2 is your list).
- The resolver keeps its contract: VAT-like ID inherits from the nearest level that has one, and `tax_inputs` returns exactly the same engine inputs as before for every P1b golden fixture. Add fixtures: department with its own `uid_ch` overriding the organisation's `vat`; person with an `ein` only; a party with a `company_register` entry and no VAT-like ID.
- **Business without a tax ID (decided):** `business_status = auto` stays as P1b (organisation = business). A *person* who trades without a VAT ID (e.g. an Austrian Kleinunternehmer) is set to `business` explicitly; add free-text `tax_status_note` on the party ("Kleinunternehmer, no UID") shown on the Tax tab. The resolver's reason list gains `explicit_without_tax_id`. **Engine behaviour must not change:** an EU business buyer without a verified VAT ID still gets domestic treatment plus a warning, never reverse charge. Add a golden fixture proving it, and one for a domestic Austrian sale to such a party (normal VAT, no warning about the missing ID).
Tests (real Postgres): migration up/down on seeded data; uniqueness; primary-per-group rule; format validation (valid and invalid examples per kind, EL/GR); isolation matrix; the golden fixtures above.
**Mutations, a real FAIL line each:** let `explicit_without_tax_id` produce reverse charge; drop the primary-per-group rule; skip normalisation for `uid_ch`. Revert.

## Part 2 — verification providers and name matching
- Pure module `apps/api/billing/parties/verification.py` with a `TaxIdVerifier` interface: `supports(kind, country)`, `check(tax_id, party_data, requester) -> VerificationResult`. `VerificationResult`: `status` (`valid` | `invalid` | `unavailable` | `not_configured` | `not_checkable`), `registered_name`, `registered_address`, `registration_active`/`gst_registered` where the registry says so, `consultation_ref`, `name_match`, `address_match`, `raw` (stored), `checked_at`. Providers are in `services/verification/` with an **injectable transport each**, registered by data (kind + country → provider).
- **VIES provider** (`vat`, EU + `XI`): as P1b, plus **requester data**: if the company has its own VAT ID, send it with the party's name/address to obtain the approximate-match answer and the consultation identifier, and store both. If the company has no VAT ID of its own, run the plain check and mark the result `simple` (not `qualified`) in the stored record and on screen. Do not claim in code, UI or docs that this equals a tax authority's confirmation procedure; the record says what was requested and what came back.
- **Swiss UID provider** (`uid_ch`) and **ABN provider** (`abn`, needs `ABN_LOOKUP_GUID` in the environment; without it return `not_configured` with a sentence telling the operator how to obtain the GUID, never an error and never `invalid`): implement exactly what the official documentation you read in Step 0 allows. ABN: store entity name, ABN status and GST registration state.
- **`not_checkable`** for kinds and countries without any provider (US EIN, free-text kinds, GB until someone asks). **Manual confirmation** (Part 4) is the route for those.
- **Mapping rule, unchanged and tested for every provider:** failing to *obtain* an answer (timeout, 5xx, rate limit, malformed body, member state down, missing configuration) is `unavailable` or `not_configured`, **never `invalid`**. `invalid` only when the registry positively says so. For ABN/UID "cancelled" or "no longer VAT-registered" is a positive answer: store it as `invalid` with the reason in `raw`.
- **Name matching**, pure, in `billing/parties/name_match.py`, thresholds and the legal-form token list in a data file: normalise case, diacritics, punctuation, spacing and legal-form words (GmbH, Gesellschaft m.b.H., AG, KG, OG, e.U., Ltd, Limited, LLC, Inc, Pty, SA, SARL, S.r.l., BV, B.V., and so on, extend sensibly); compare the party's legal name with `registered_name`; result `match` | `partial` | `mismatch` | `unknown`. `unknown` when the registry returned nothing usable (some member states return placeholders instead of a name; treat placeholders such as "---" as no name). Never auto-correct the party's data. Address comparison only as `match` | `differs` | `unknown`, informational.
- Golden fixtures: "ORF Österreichischer Rundfunk" vs "Österreichischer Rundfunk" (partial or match, say which and why), "Mustermann GmbH" vs "MUSTERMANN GESELLSCHAFT M.B.H." (match), "Alpha Film GmbH" vs "Beta Media GmbH" (mismatch), registry returns placeholder (unknown), diacritics and ß, a name differing only by punctuation.
Tests use fake transports only; **tests never reach the network**. Each provider: valid, invalid, malformed, timeout, 5xx, rate limit, not configured.
**Mutations, a real FAIL line each:** map a timeout to `invalid` in each provider; treat `unknown` as `match`; compare without legal-form stripping; send no requester data although the company has its own ID. Revert.

## Part 3 — check policy, scheduler, change detection
- **Policy (company settings, defaults [Guessing], all editable):** `initial_check_offsets` default `[0 days, 1 day, 7 days]` (a new or changed ID is checked at creation, then again after a day and after a week, so a registry that has not caught up or a typo is visible); `recheck_interval_days` default 90, choices 7 / 30 / 90 / 180 / 365 / off; per-party override of the interval; `max_check_age_days` default 180: a party's `buyer_vat_verified` is false when the latest valid check for its current ID is older than this. Validate the combination (age must be at least the interval unless interval is off) with a readable error.
- **Scheduler:** a Celery beat task `tax_id_checks.run_due` (hourly) selects due IDs with `FOR UPDATE SKIP LOCKED`, per-provider rate limiting with jitter, no more than a small configurable batch per run. An `unavailable` result does **not** count as a completed check: schedule a retry (6 h, then 24 h, then wait for the next regular slot) and keep the previous verified state until `max_check_age_days` runs out. Add the beat process to the dev and the server-test compose files; the self-hosted default must work with no internet (results `unavailable`, nothing breaks).
- Extend the append-only check table (keep its UPDATE/DELETE trigger, test that it still holds): `tax_id_id`, `provider`, `trigger_kind` (`manual` | `initial` | `scheduled` | `retry` | `on_change`), `qualified` (bool/`simple`), `name_match`, `address_match`, `registered_name`, `consultation_ref`.
- **Change detection**: compare each completed check with the previous completed one for the same ID. Changes that matter: status changed (valid ↔ invalid), registered name changed, name match worsened to `mismatch`, GST/VAT registration lost. Each emits audit `party.tax_id_change_detected` (diff, in the same transaction) and sets the ID's `needs_attention` until someone acknowledges it with a note (`party.tax_id_change_acknowledged`). A changed ID value or country resets verification and restarts the initial series (as P1b's reset rule, now per ID).
- **Surfacing**: a computed `needs_attention` list; per Step 0 item 4, send a notification only through an existing mechanism. Do not build a new one here.
- **Evidence for documents (P2 will need it):** `tax_inputs` also returns `tax_id_evidence` = `{tax_id_id, kind, value, check_id, status, qualified, checked_at, consultation_ref, provider}` of the check `buyer_vat_verified` relied on, or null. It is part of the detached resolved value object, so P2 can snapshot it.
- **Non-EU business buyers:** the engine is untouched. The party layer adds a warning in `tax-preview` when a business buyer outside the EU has no ID that is `valid` and no current manual confirmation: "no proof of business status on file". Warning only, never a block.
Tests (real Postgres): due selection and ordering; two concurrent runs never double-check the same ID (use two real connections); unavailable retry schedule; initial series completes then interval applies; stale check flips verified to false; policy validation; change-detection table (every change type, and no change = no event); acknowledge flow; trigger still blocks UPDATE/DELETE; evidence matches the check used.
**Mutations, a real FAIL line each, and for each pick the row only that guard protects:** remove `SKIP LOCKED` (two-connection test must fail); count `unavailable` as a completed check; ignore `max_check_age_days`; skip change detection on name change; drop the reset on value change. Revert.
