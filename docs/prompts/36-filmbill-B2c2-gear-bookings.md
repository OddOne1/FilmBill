## Part 1 — model and the availability rule (pure, then database)
- **Pure module** `billing/planning/gear_availability.py` (same import boundary as the calc engine: no SQLAlchemy, no FastAPI; a second test proving the probe can fail). Inputs per device and day: `owned`, the list of bookings that day (`quantity`, `status`, `booking_id`). Outputs per day: `owned`, `scheduled`, `booked`, `available = owned − scheduled − booked` (may be negative), `overbooked = available < 0`, `shortage = max(0, −available)`; over a period: the **lowest day** governs (`min_available`, `worst_day`) per SCOPE §4.4.7. A cancelled booking never counts. Ints only; golden fixtures as data files (state every number): (a) owned 3, nothing booked → available 3; (b) owned 3, booked 2 + scheduled 1 on a day → 0, not overbooked; (c) owned 3, booked 2 + scheduled 2 → −1, shortage 1; (d) a cancelled booking ignored; (e) the same booking never counted against itself when it is edited; (f) a three-day period where only the middle day is short → worst day is the middle one; (g) owned 0 with a booking → overbooked by that quantity.
- Migration, company-scoped, soft deletion only:
  - `gear_bookings`: `project_id`, `block_id` (a strip of that project), `device_id`, `quantity int >= 1`, `status` (`scheduled | booked | cancelled`), `status_note`, `booked_on`, `booked_by`, `added_via_booking_id` nullable (the parent booking when this row was added as a dependency), `follows_parent bool` (true while its quantity is still derived from the parent), `overbooking_note` nullable, `removal_note`, timestamps. Unique active (block, device, `added_via_booking_id`-or-null) so the same device is not booked twice on the same strip by the same route.
  - `gear_booking_days`: `booking_id`, `date` (inside the strip's range). On creation: every strip day that is not `off`; days can be unticked.
- Audit: `gear_booking.created|updated|status_changed|days_set|removed`, bulk = one event with counts; dependency additions are one event listing the rows.

## Part 2 — API
- **Availability:** `GET /devices/{id}/availability?from=&to=` (per day numbers plus who holds it: project, strip, status, quantity) and `GET /gear/availability?from=&to=&category=&q=` (many devices, for the planner). Available to `devices.view` + `projects.view`.
- **Booking:** create one or many bookings on a strip (device, quantity, days default) with the **dependency step** (below); update quantity and days; set status single and bulk; remove (= `cancelled` with a note, never deleted). Every create/update response carries a `warnings` list: overbooking (shortage, worst day, who holds the device: project, strip, status, quantity) and `alternatives` (the device's configured alternatives in order, each with its **own availability for the same days**, the note and the price hint). **The save is never refused for overbooking**; the booking is stored and flagged; an optional `overbooking_note` records why ("renting in").
- **Dependencies at booking time (SCOPE 4.4.3), one level only:** booking a parent adds each of its `always` associations automatically as separate bookings (`quantity = parent quantity × quantity_per_parent`, `added_via_booking_id` set, `follows_parent = true`, same days and status as the parent); `ask` associations are returned as **suggestions** with their pre-calculated quantity and are added only if the client sends them chosen (the web shows a checkbox popup). **An associated device's own associations are never pulled in** (no chains, no loops); a test proves a three-level chain adds exactly one level. Changing the parent's quantity recalculates dependents that still `follow_parent`; a dependent whose quantity was edited by hand stops following (and the response says so). Removing a parent does **not** silently remove its dependents: the response lists them and the client asks (cancel them too, or keep them), both choices audited. Dependents can be removed on their own with a note.
- **Strip and project summaries:** `GET /projects/{id}/gear` (per strip: bookings with device, quantity, status, thumbnail, warnings) with counts and a **total weight** (`quantity × weight_kg`, plus "n items without weight"); no prices anywhere.
- **Permissions:** view needs `projects.view` and `devices.view`; changes need `projects.edit`; missing permission answers 404; staff can see gear bookings (gear is visible to staff), nothing cost-related is involved.
Tests (real Postgres): create with default days (an `off` day excluded) and with unticked days; status paths and bulk; the overbooking warning with another project holding the gear (state the numbers) and the save succeeding; alternatives with their availability; `always` dependency quantities (2 batteries per camera × 3 cameras = 6), `ask` suggestions not added unless chosen, no second level, no loop; parent quantity change recalculating only followers; removal of a parent with its dependents listed; weight total with and without missing weights; isolation rows; permission matrix; no DELETE route. **Mutations, a real FAIL line each:** overbooking refuses the save; the dependency step follows a second level; an `ask` association is added without being chosen; a cancelled parent leaves its dependents counted as booked without the question.
