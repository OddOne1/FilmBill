## Part 1 — the pure tracking module and its fixtures
`apps/api/billing/budget/tracking.py`, pure Python, same import-boundary test as `billing/calc` (no SQLAlchemy or FastAPI imports, a second test proving the probe can fail). `Decimal` only; entries are already 2 dp, so no rounding other than a final `quantize` to 2 dp on sums.
Inputs per line: `estimate_cost`, a list of commitments (`amount`, `status`, `voided`), a list of actuals (`amount`, `voided`, optional `commitment_id`), optional `etc`. Outputs per line, section and budget:
- `committed_gross` (sum of non-voided, non-cancelled commitments) and **`committed_open`** = for each open commitment, `max(0, commitment.amount − sum of non-voided actuals linked to it)`; closed commitments contribute 0, cancelled and voided contribute 0.
- `actual` (sum of non-voided actuals, linked or not).
- **`exposure`** = `actual + committed_open` (what is spent or owed). **Never** `actual + committed_gross`: a commitment that has been invoiced must not count twice. This is the rule most likely to be gotten wrong; it gets its own fixtures and its own mutation.
- **`remaining`** = `etc` if the user set one, otherwise the default rule `max(estimate_cost − actual, committed_open)`.
- **`efc`** (estimate at completion) = `actual + remaining`.
- `variance` = `estimate_cost − efc` (positive = under budget), `variance_percent` (`None` when the estimate is 0), `over_budget` = `efc > estimate_cost`.
- Section and budget totals are sums of their lines **plus entries that carry a section but no line** (see Part 2): those add to `actual`/`committed_open` and to `efc` as-is (`remaining` is 0 for them), and are reported separately as `unallocated`.
- **Forecast margin** at budget and section level = `price − efc` and as a percent of price, where `price` is the estimate-phase client price from the calculation engine. State plainly in the code comment and the docs that this uses the estimate price, because the client price does not move when costs do.
- **This default rule is [Guessing].** Write it up in SCOPE as an open decision for Mathias (not the Steuerberater) and make the rule's name visible in the API response (`remaining_rule: "etc" | "default"`).
Golden fixtures as data files next to the tests (state every number): (a) a line with estimate 1,000, no entries → remaining 1,000, efc 1,000; (b) estimate 1,000, actual 400 → remaining 600, efc 1,000; (c) estimate 1,000, actual 1,200 → remaining 0, efc 1,200, over_budget; (d) estimate 1,000, open commitment 700, no actual → committed_open 700, remaining max(1,000, 700) = 1,000, efc 1,000; (e) the same commitment partly invoiced: actual 300 linked → committed_open 400, exposure 700, not 1,000; (f) commitment fully invoiced by actuals of 700 → closed, committed_open 0, exposure 700; (g) commitment of 700 invoiced at 750 → committed_open 0, actual 750, no negative open amount; (h) etc set to 200 with actual 400 → efc 600, rule `etc`; (i) voided actual and voided commitment excluded; (j) section-only entry of 150 → in section and budget `actual` and `unallocated`; (k) the A1/A2 S1 example budget with an actual of 3,200.00 on the Studio line, an open commitment of 1,000.00 on the Alexa line (cost 0.00) and an etc of 500.00 on the Taxi line: compute and state every section's estimate, committed_open, actual, efc, variance, and the forecast margin against the net price 12,517.20.

## Part 2 — data model and API (migration, rule 9)
All tables carry `company_id` and join the cross-company isolation test. **No hard delete**: entries are voided with a reason, never deleted; assert no DELETE route on the OpenAPI document.
- `budget_commitments`: `budget_id`, `section_id` (required), `line_id` (nullable, must belong to that section), `party_id` (nullable, same company) and `payee_text` (free text when no party), `description`, `reference` (PO or agreement number), `amount NUMERIC(18,2)` (**net, company currency**, > 0), `commitment_date`, `status` (`open` | `closed` | `cancelled`), `notes`, `voided_at`, `void_reason`, timestamps. A commitment closes automatically when linked non-voided actuals reach or exceed its amount, and may be closed or cancelled by hand with a reason (audited); it reopens automatically if a linked actual is voided.
- `budget_actuals`: `budget_id`, `section_id` (required), `line_id` (nullable), `commitment_id` (nullable, same budget), `party_id`/`payee_text`, `description`, `reference` (supplier invoice number), `amount NUMERIC(18,2)` (net, > 0; corrections are a new entry plus a void, not a negative amount), `incurred_on`, `paid_on` (nullable), `notes`, `voided_at`, `void_reason`, timestamps.
- `budget_lines.etc NUMERIC(18,2)` nullable (the user's own estimate of what is still to be spent on the line).
- **Locking (decided):** a locked budget freezes the **estimate** (sections, lines, globals, adjustments) exactly as in A2. **Commitments, actuals and ETC remain editable on a locked budget**, because a locked estimate is the baseline these are measured against. Test it both ways.
- **Duplicate warning (non-blocking):** creating an actual or commitment whose (party or payee text, reference, amount) matches an existing non-voided entry in the same budget returns a `duplicates` list in the response; the UI shows it and still allows saving.
- **Duplicating a budget** copies the estimate only, never entries (amend the A2 duplicate test to assert this).
- **Permissions: no new keys.** Read = `budgets.view`, write = `budgets.edit`; staff still see nothing (the A2 staff walk test must cover the new routes, and the surface-count assertion must be updated deliberately).
- **Audit** (caller's transaction, diffs): `budget_commitment.created|updated|closed|cancelled|voided`, `budget_actual.created|updated|voided`, `budget_line.etc_set`, `budget.actuals_import_applied` (counts). Bulk operations write one event with counts.
- **Endpoints:** commitments and actuals list/create/update/void with filters (section, line, party, status, date range, voided yes/no), `POST` close and cancel for commitments, `PUT /budgets/{id}/lines/{line_id}/etc`, and **`GET /budgets/{id}/tracking`** returning the Part 1 output for every line, section and the budget (the web never computes money; it renders this). Keep `GET .../calculated` unchanged and make `tracking` reuse its estimate numbers, not recompute them.
- **CSV import of actuals** (the bridge from bank or card exports and spreadsheets): `import/preview` and `import` with A2's plan, digest and apply pattern; columns `date;description;payee;reference;amount;section_code;line_description;paid_on`; German decimal comma and the ambiguous-dot refusal from A2's CSV fix; a row without a resolvable section is an error row; a row that duplicates an existing entry is flagged `duplicate` in the preview and skipped unless the user ticks it; never voids or edits existing entries. Plus `GET .../actuals/export.csv` in the same format.
Tests (real Postgres, declared): migration up/down; entry validation (line must belong to the section, linked commitment must belong to the same budget, amount > 0, party from another company = 404); automatic close and reopen of commitments; voiding behaviour and its effect on `tracking`; `tracking` equals the Part 1 module for the fixtures (including (k)); lock behaviour both ways; duplicate warning; duplicate-budget copies no entries; CSV preview equals applied; permission and isolation matrix including the staff walk; no-DELETE assertion.
